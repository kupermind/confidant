# Граница: `backend/` ↔ пользовательский слой

Состояние на 2026-10-05, после PR #11. Документ передачи между двумя разработчиками: кто за что
отвечает, с чем именно говорит UI, что он обязан подготовить и как меняется контракт. Если страница
расходится с кодом, прав код — страницу правят в том же PR.

## 1. Кто за что отвечает

| Сторона | Отвечает за | Каталоги |
|---|---|---|
| **Крипто/ZK-лид** | Rust-ядро; **кворумные сервисы**: узел верификатора (`confidant-node`), сайдкары подписантов, координатор, скрипты настройки пула и запуска; CLI-инструмент; оба e2e-харнеса; аудиторский цикл | `core/`, `backend/`, `e2e/testnet/`, `docs/audit/`, `docs/*.md` |
| **API/XRPL-лид** (владелец репозитория) | **пользовательский слой**: UI, UX локального кошелька, депозитный Payment с собственного XRPL-аккаунта пользователя, ссылки на explorer, предзаполнение пула, демо-сценарий и питч | `frontend/`, `scripts/` |

Шов — HTTP. UI является **клиентом координатора** (один процесс, ключей не держит). На стороне UI
нет ключей пула и подписантов, состояния верификатора и логики проверки депозитов; на стороне
бэкенда нет пользовательских ключей трат и никакого рендеринга.

## 2. Контракт, который потребляет UI — координатор

Базовый URL: `http://127.0.0.1:7200` при запуске через `backend/quorum/start-all.mjs` (настраивается).
Всё в JSON. Ошибки — `{ "error": "<сообщение>", "details"?: {…} }` со статусами:

| Статус | Смысл | Типичные сообщения |
|---|---|---|
| 400 | кривой запрос или лимит ядра | нулевая сумма, слишком много выходов, плохой hex, нет полей |
| 409 | отказ верификаторов | nullifier уже потрачен (повтор / двойная трата), несовпадение memo, неизвестный якорь, `only 1/3 signers endorsed (quorum 2)`; перевод комиссий больше доступного / уже учтён |
| 422 | леджер не подтверждает утверждение | депозит не validated / не в пул / не та сумма / нет memo `confidant/shield`; анкорная транзакция не несёт этот корень |
| 403 | отказ политики скрининга узла (необязательная, у каждого узла своя) | `account r… is on the screening list` (окончательно); `deposit … younger than the standby … retry at ledger N` (повторить позже) |
| 502 | недоступен RPC леджера или узел | `txnNotFound <hash>` для выдуманного хеша депозита, `fetch failed` |

### Эндпоинты

| Вызов | Тело | Ответ |
|---|---|---|
| `GET /state` | — | `PoolState` |
| `GET /log?from=N` | — | `{ records: BundleRecord[], …PoolState }` — зеркало, с которого синхронизируется кошелёк; `records` сохранить как `log.json` |
| `POST /submit/shield` | `{ record, depositTxHash }` | `Accepted` + поля кворума |
| `POST /submit/transfer` | `{ record }` | `Accepted` + поля кворума |
| `POST /submit/unshield` | `{ record, destination }` | `Accepted` (с `payout`) + поля кворума, включая `payoutTx` / `payoutBlob` |
| `POST /audit/reveal` | `{ viewingKey }` | `RevealReport` |
| `GET /config` | — | `{ network, explorer, xrplWs, pool, sink, quorum, signers, fees: { shieldBps, unshieldBps, treasury }, credential: { issuer, type, typeText } \| null, nodes: [url…] }` — публичные факты для UI; без секретов. `nodes` — URL, по которым браузер достигает каждый узел (по умолчанию `/node/<i>` на origin UI), для проверки доказательства средств |
| `GET /fees` | — | `FeeReport` узла координатора |
| `GET /policy` (узел) | — | `{ credential: { issuer, type, typeText } \| null, screening: { active, standbyLedgers } }` — ворота депозитов, которые узел применяет; координатор копирует `credential` в `GET /config` |
| `POST /fees/sweep` | `{ amount? }` (дропы; по умолчанию всё доступное) | `{ amount, tx, treasury, recorded, refusals }` — вызов оператора, k-of-N Payment пул → казна |
| `POST /pof/verify` (узел, доступен как `/node/<i>/pof/verify` — никогда через координатор) | `{ record, amount, challenge: { borrower, lender, ledgerIndex, expiry } }` | `{ ok, amount, challenge, validatedLedger, root, bundleHash, meaning, credential: { subject, credentialType, credentialTypeText, expiration, uri, uriText } \\| null, credentialRefused }` — доказательство средств, проверенное только чтением на собственном состоянии узла; не логируется и не сохраняется; `credential` — XLS-70 Credential, который этот узел позволил бы подписать сайдкару. 400 challenge отклонён · 409 доказательство не проходит · 413 тело > 256 КиБ · 429 узел занят · 502 нет валидированного леджера / леджер L не читается |
| `POST /pof/credential` | `{ record, amount, challenge }` | `{ tx, issuer, subject, credentialType, credentialTypeText, expiration, uri, amount, challenge, validatedLedger, signers, refusals }` — кворум записывает проверенное доказательство как истекающий `CredentialCreate` с аккаунта пула на заёмщика; каждый сайдкар перепроверяет на своём узле в момент подписи. 409 меньше k подписантов подтвердили · 502 леджер |

Формы (на проводе camelCase):

```jsonc
PoolState   { root, anchoredRoot | null, leafCount, nullifierCount, bundleCount, consumedDeposits }
Accepted    { bundleIndex, firstLeaf, newRoot, bundleHash, nullifiers[], commitments[], fee, payout?: { destination, amount } }
FeeReport   { shieldBps, unshieldBps, treasury | null, accrued, swept, available, poolExcess | null, outstandingBacking }   // available = min(accrued − swept, poolExcess); poolExcess = баланс пула − стоимость нот, с леджера
кворум      { memoHex, anchorTx, payoutTx | null, payoutBlob | null, payoutError | null, signers: [rAddr…], refusals: [string…] }
RevealReport{ balance, notes: [{ direction: "incoming" | "outgoing", amount, leafIndex, bundleIndex, timestamp, spent, recipient? }] }
```

- `anchorTx` / `payoutTx` — хеши транзакций XRPL: ссылка `https://testnet.xrpl.org/transactions/<hash>`.
- Submit **блокируется до валидации анкора (и выплаты) в XRPL**: 5–15 с. Показывать прогресс.
- `payoutBlob` — мультиподписанная выплата. Если установлен `payoutError`, нота уже потрачена, а
  пользователь не оплачен; UI (или кто угодно) может переотправить блоб командой XRPL `submit` до его
  `LastLedgerSequence` либо просто повторить `POST` с теми же `{record, destination}` любому
  координатору (`/endorse` идемпотентен, сайдкары подпишут заново). Не показывать «оплачено», пока
  нет `payoutTx`.
- Суммы — в **дропах** (числа в `Accepted.payout.amount`, строки в полях XRPL).
- **Протокольная комиссия (настраивается на сервере, UI только показывает).** `GET /config.fees`
  даёт ставки в базисных пунктах. **Shield:** депозит — брутто-сумма, которую ввёл пользователь; UI
  обязан построить ноту на `gross − floor(gross · shieldBps / 10000)` и внести `gross` — нота на
  любую другую сумму отвергается с 422 (`delivered == value_balance`). **Unshield:** нота сжигается на
  введённую сумму; `payout.amount` в ответе — нетто, которое получит адресат
  (`gross − floor(gross · unshieldBps / 10000)`); показывать обе. **Переводы бесплатны.**
  `Accepted.fee` — комиссия, взятая кворумом, в дропах. В UI комиссия не настраивается, не
  редактируется и не платится отдельно; казна публична, весь учёт комиссий проверяем по леджеру.
- **Всего в пуле / total shielded (показывает UI, публично).** `GET /fees.outstandingBacking` — стоимость всех нот,
  которые обеспечивает пул, в дропах (shield'ы минус unshield'ы по публичным value balance). Она
  публична по построению — каждый shield и unshield есть Payment на леджере, — поэтому UI показывает
  её как «Total shielded — N XRP (backed, public)» рядом с приватным балансом держателя и никогда
  наоборот. Это стоимость обеспеченных нот, а не весь XRPL-баланс аккаунта пула (там ещё средства
  оператора, невыведенные комиссии и отклонённые депозиты до возврата) — об этом говорит подсказка; приватно
  только то, как сумма разделена между держателями и кто кому платил внутри.
- **Баланс аккаунта пула и сумма в пуле.** UI показывает сумму в пуле как заметную цифру в шапке (слева от
  индикатора состояния) со второй строкой из того же ответа `GET /fees`, а `frontend/balances.html` сводит обе цифры
  вживую по леджеру и отвечает на частые вопросы (memo, случайные XRP, комиссии, средства оператора, анкоры). Строка:
  «аккаунт пула B XRP = `outstandingBacking` в пуле + `poolExcess` средства оператора и невыведенные
  комиссии» (B — их сумма; `poolExcess` — собственное чтение узлом «баланс − обеспечение», `null`, если
  леджер недоступен). Излишек — это средства оператора при создании пула, ещё не переведённые в казну
  комиссии и отклонённые депозиты, ожидающие возврата, — никогда не стоимость нот.
- **Восстановление shield.** Как только депозит-Payment валидирован, UI хранит record и хеш депозита локально до
  подтверждения анкора; после потерянного ответа или перезагрузки он предлагает «Resume anchoring» — повторную
  отправку того же record в `/submit/shield`. Узел идемпотентен для бандла, который является его последней записью;
  409 (nullifier уже потрачен) при повторе означает, что shield был применён раньше, и UI считает его выполненным.
- **Ключ просмотра — это авторизация для `/audit/reveal`**, он раскрывает всю историю держателя
  (только чтение, ничего более). UI отправляет его только тому координатору, которого выбрал
  пользователь, по настроенному пользователем URL, и предупреждает перед отправкой; никогда не
  хранит и не пересылает его. CORS стоит `*`, потому что у координатора нет ничего, что мог бы
  забрать чужой origin — ключ остаётся риском пользователя.

Полный клиент этого контракта со всеми негативными случаями — `e2e/testnet/run-services.mjs`.

### Ворота по Credential (фича хакатона A) — контракт между узлом и стороной держателя

*Предложено 2026-10-24 (день события); в тот же день реализовано с обеих сторон (`backend/node/src/credential.rs`,
`frontend/issuer.html`, строка Compliance в приложении). Узел сообщает свои ворота через `GET /policy`, координатор
копирует их в `/config.credential`.*

- **Конфиг.** `GET /config` получает `credential: { issuer: "r…", type: "<hex>", typeText: "ConfidantKYC",
  expiresAfter?: <секунды> } | null`. `null` (или отсутствие) — ворота выключены, UI ничего не показывает.
  Эмитента и тип UI берёт отсюда и больше ниоткуда.
- **Правило.** Shield принимается, только если `Account` депозита держит на леджере XLS-70 Credential с
  `Issuer == credential.issuer`, `CredentialType == credential.type`, установленным флагом **accepted**
  (`lsfAccepted`) и не истёкшим `Expiration`; каждый узел читает это с леджера сам (`ledger_entry`
  `credential` или `account_objects` депозитора) при submit и снова при endorse. Сайдкар не подписывает то,
  чего не принял его собственный узел (правило без изменений).
- **Отказ.** HTTP **403** с `{ error: "no accepted credential from <issuer> of type <typeText> for <account>" }`
  — то же семейство статусов, что у скрининга; UI различает по слову `credential`. Выпущенный, но не
  принятый Credential тоже отклоняется (принять его должен субъект: эта подпись и привязывает аккаунт).
- **Сторона держателя (UI).** В карточке кошелька строка *Compliance*: `verified ✓` / `verified — нажмите
  Confirm` / `not verified — как пройти проверку`; *Confirm* подписывает `CredentialAccept { Account: держатель, Issuer,
  CredentialType }` XRPL-аккаунтом держателя в браузере (xrpl.js); отклонённый shield ссылается на страницу
  эмитента. Пока узел не отдаёт `credential` в `/config`, страница эмитента передаёт держателя по ссылке
  `/?accept=<issuer>:<typeHex>`, которую приложение сохраняет и считает конфигом ворот (только демо-путь).
  Демо-эмитент — статичная страница (`frontend/issuer.html`): пополненный из faucet XRPL-аккаунт в
  роли KYC-провайдера, подписывает `CredentialCreate { Account: issuer, Subject: holder, CredentialType,
  Expiration? }` для любого вставленного адреса и печатает свой адрес и тип для конфига операторов узлов.
  Честная подпись: эмитент — демо-персона; ворота на леджере настоящие.
- **Библиотека в браузере.** В xrpl.js 4.3.0, который грузило приложение, типов транзакций XLS-70 нет; страница
  держателя и страница эмитента используют **xrpl.js 5.3.0** (та же версия, что в `backend/quorum`).

### Доказательство средств (фича хакатона C, Tier 1 — сторона чтения)

*Построено 2026-10-24 (день события) поверх слайса ядра (`core`: `OpTag::ProofOfFunds`, домен `ConfidantPoF_v1_`).
Сторона узла: `backend/node/src/pof.rs` и `POST /pof/verify`; сторона держателя: экспорт wasm
`buildProofOfFunds(amount, challenge)` и операция воркера `pof({ amount, challenge })` (одно имя на всех поверхностях: операция воркера, маршрут wallet-сервиса, эндпоинт узла). Путь подписи
`credential-pof` (кворум записывает истекающий Credential на аккаунт заёмщика) — отдельный слайс под правилом
отгрузки из `docs/PROOF-OF-FUNDS.md` §6.*

- **Challenge.** Кредитор заполняет `{ borrower, lender, ledgerIndex, expiry }`: `borrower` — классический XRPL-адрес
  заёмщика (X-адреса отклоняются, чтобы обе стороны подписывали одни и те же байты); `lender` — непрозрачный идентификатор
  (имя, аккаунт, id запроса) из 1–64 печатных символов без `|`; `ledgerIndex` — индекс валидированного леджера, который
  кредитор видел, выдавая challenge; `expiry` — индекс леджера после него и не более чем на 21 600 леджеров (≈ 24 ч)
  позже. **Канонические байты** — над чем подписывает кошелёк держателя и что каждый узел пересчитывает из полей — это
  UTF-8-строка `confidant/pof/v1|<borrower>|<amount>|<ledgerIndex>|<expiry>|<lender>`. UI строит ровно эту строку и
  передаёт её в `pof({ amount, challenge })`; `amount` в дропах.
- **Проверка.** Кредитор — или держатель от его имени — отправляет `{ record, amount, challenge }` POST'ом **каждому
  узлу** по URL из `/config.nodes` (`/node/<i>/pof/verify` на origin UI). Координатор не на пути и record не видит.
  Узел проверяет поля, судит свежесть по индексу валидированного леджера, **который читает сам** (`ledgerIndex` не
  старше 200 леджеров, `expiry` после него), пересчитывает байты и выполняет проверку только чтением на своём
  состоянии. Ответ: `{ ok: true, amount, challenge, validatedLedger, root, bundleHash, meaning }` — `root` — состояние
  этого узла, на котором проверено доказательство, `meaning` — честная подпись для показа дословно. Ошибки: **400**
  `proof of funds: challenge refused: …` (поле или окно свежести), **409** доказательство не проходит на состоянии этого
  узла (другая сумма, другой challenge, запись пула, ноты с тех пор потрачены), **413** тело больше 256 КиБ, **429** узел
  занят (четыре проверки одновременно — повторить), **502** узел не может прочитать валидированный леджер.
- **Не логируется, не сохраняется.** Record несёт nullifier'ы держателя; узел не держит копии и ничего о запросе не
  пишет, даже хеш бандла. UI не должен отправлять его координатору и хранить дольше сессии; кошельку держателя стоит
  затем перевести доказанные ноты себе (иначе узлы могут связать позднюю трату — `docs/PROOF-OF-FUNDS.md` §1).
- **Честная подпись (поверхность кредитора, дословно из `meaning`):** «некто, контролирующий не менее `amount` в этом
  пуле, ответил на этот challenge на момент валидированного леджера: сигнал для андеррайтинга, снимок, не блокировка и
  не доказательство, что ноты принадлежат заёмщику». k вердиктов от N узлов — это k независимых чтений одного и того же
  восстановимого с леджера состояния; сколько их нужно, решает кредитор. На леджер в этом слайсе ничего не попадает.
- **Сторона держателя (UI, построено 2026-10-24).** Четвёртая вкладка **Prove funds**: сумма, заёмщик (предзаполнен
  XRPL-аккаунтом держателя), id кредитора, срок (1 / 6 / 24 ч → 900 леджеров в час). Приложение само читает индекс
  валидированного леджера, строит challenge и каноническую строку, доказывает в браузере (`pof`), отправляет
  `{ record, amount, challenge }` POST'ом на **каждый** URL из `/config.nodes` и показывает таблицу вердиктов по узлам
  (✓ / отказ, леджер, по которому судили, корень этого узла), честную подпись и **пакет доказательства**
  `{ amount, challenge, record, bundleHash }` — скопировать или скачать для кредитора. Затем предлагает **ротировать
  ноты** (перевод на собственный адрес, предзаполненный на вкладке Transfer), чтобы узлы не связали следующую трату с
  доказательством. Пакет не отправляется координатору и не сохраняется.
- **Страница кредитора (`frontend/lender.html`, построена 2026-10-24).** Шаг 1 — текст запроса заёмщику (id кредитора,
  минимальная сумма, срок). Шаг 2 — вставленный или загруженный пакет: проверка формы, что он утверждает (сумма, заёмщик
  со ссылкой на explorer, id кредитора — с пометкой, если не свой, окно леджеров и сколько ещё действует), POST на каждый
  узел из `/config.nodes`, таблица вердиктов с «k из N узлов подтвердили» и `meaning` узлов дословно; 400 (устарел /
  истёк) и 409 (не проходит) объяснены. Карточка «что сказано / что не сказано / не блокировка» закрывает страницу.
  `?demo=1` имитирует четыре узла (один занят, 429) и загружает демо-пакет.
- **На леджере (путь подписи, построен 2026-10-24 — отгружается только со своим IMPL-PASS).** Когда k из N узлов
  подтвердили, вкладка Prove funds предлагает *записать на леджер как Credential*: `POST /pof/credential` с тем же телом.
  Ответ называет транзакцию `CredentialCreate` и поля; затем приложение предлагает **Confirm with my signature** —
  `CredentialAccept { Account: заёмщик, Issuer: пул, CredentialType }`, подписанный в браузере XRPL-аккаунтом держателя
  (аккаунтом из challenge; для другого аккаунта приложение отказывается). Оба попадают в Activity. `Expiration` Credential
  — `close_time(L) + 4 с × (E − L)`, `URI` — текст `confidant/pof/v1|X|L|E|<digest16>`; оба выводит каждый узел, поэтому
  сайдкары подписывают только то, что вычислил их узел. Шаг 3 страницы кредитора читает credentials заёмщика с леджера
  (`account_objects type credential`, issuer = пул, тип `ConfidantPoF`), сообщает accepted / issued / expired со временем
  истечения, декодирует URI и говорит, совпадает ли он с проверенным пакетом (`credential.uri` узлов из вердиктов).
  Честная подпись на обеих поверхностях: credential говорит «контролировал ≥ X на момент леджера L», а не «контролирует
  сейчас».

## 3. Что обязан подготовить UI — `record`

`record` — это `BundleRecord` ровно в том виде, в каком его записал кошелёк (поля не трогать):

```jsonc
{ index, op: "shield" | "transfer" | "unshield", timestamp, external, anchor, flags, valueBalance,
  firstLeaf, actions: [{ nullifier, rk, cmx, … }], proof, bindingSignature }
```

Его выдаёт кошелёк держателя — на хакатоне CLI (`cargo build --release --example cli`), позже
локальный процесс над `confidant_core::Wallet`. Файл `*.wallet.json` содержит **ключи трат** (0600,
громкое предупреждение); он не покидает машину пользователя и никуда не отправляется.

| Сценарий | Шаги |
|---|---|
| **Синхронизация** | `GET /log?from=0` → записать `records` в `log.json`. Его принимает каждая сборка ниже. |
| **Shield** | 1. `cli wallet --file u.wallet.json build-shield <drops> shield.json log.json` → печатает `{ bundleHash, file }`. 2. XRPL-аккаунт пользователя отправляет `Payment` ровно на `<drops>` на аккаунт пула с одним memo `{ MemoType: hex("confidant/shield"), MemoData: <bundleHash hex> }`; дождаться валидации. 3. `POST /submit/shield { record: <shield.json>, depositTxHash }`. **Сначала сборка, потом депозит** — memo должно коммитить бандл; сумма должна совпасть с `delivered_amount`. 403 с упоминанием standby означает «слишком свежий депозит»: повторить после названного леджера (демо-кворум ждёт 2 леджера ≈ 8 с); 403 со ссылкой на список — окончательный, депозит остаётся на аккаунте пула до возврата операторами. |
| **Transfer** | синхронизация → `cli wallet --file u.wallet.json build-transfer <recipientAddressHex> <drops> transfer.json log.json` → `POST /submit/transfer`. В леджер попадает только анкор. |
| **Unshield** | синхронизация → `cli wallet --file u.wallet.json build-unshield <drops> <rDestination> unshield.json log.json` → `POST /submit/unshield` **с тем же destination** (его связывает подпись внутри бандла; другой адрес будет отклонён). По умолчанию — **свежий XRPL-адрес на каждый unshield** и совет вносить депозит со свежего аккаунта: адреса входа и выхода пула публичны, и их повторное использование позволяет анализу цепочки связать граничные события одного пользователя (ROADMAP §4.6). |
| **Раскрытие** | `cli wallet --file u.wallet.json info` → `viewingKey` → `POST /audit/reveal`. Показывает всю активность этого держателя и ничего более. |
| **Баланс** | `cli wallet --file u.wallet.json sync log.json` → `{ balance, synced, root }`. |

`init` создаёт файл кошелька; `info` печатает `{ address, viewingKey }` (адрес получателя = `address`, 43 байта hex).

## 4. Чем UI не занимается и чего нет в `backend/`

- UI никогда не проверяет депозиты, не вычисляет якоря, не держит ключи пула и подписантов и не
  решает, что что-то заанкорено: он передаёт `depositTxHash` и читает `anchoredRoot` / `anchorTx`.
- В `backend/` нет учётных записей, аутентификации, TLS, ограничения частоты (демо на localhost),
  хранения и бэкапа кошельков, скрипта предзаполнения (`scripts/`, владелец) и рендеринга.
- Формулировки о доверии для пользователя зафиксированы в `SPEC.ru.md` §4 и `README.md`; UI не
  должен заявлять больше (CI проверяет формулировки в спецификациях).

## 5. Запуск бэкенда для UI

```bash
cargo build --release --bin confidant-node --example cli
cd backend/quorum && npm install
SIGNERS=3 QUORUM=2 DIR=../../data/quorum npm run setup-pool        # один раз на пул (faucet testnet)
NODE_BIN=../../target/release/confidant-node DIR=../../data/quorum npm run start-all
```

| Что | Где |
|---|---|
| координатор (базовый URL для UI) | `http://127.0.0.1:7200` |
| узел координатора / узлы подписантов | `:7000` / `:7001–7003` (тот же API без полей кворума; `/log` работает на любом) |
| сайдкары подписантов | `:7101–7103` (не для UI) |
| аккаунт пула, sink, адреса подписантов, кворум | `data/quorum/config.json` (в gitignore) — UI берёт отсюда `pool` |
| ключи подписантов | `data/quorum/signer*.key.json`, 0600, в gitignore; UI их не читает |

Страницы explorer, на которые стоит ссылаться: аккаунт пула `https://testnet.xrpl.org/accounts/<pool>`
(каждый якорь — Payment на 1 дроп пул → sink с memo `confidant/anchor`), каждый депозит, каждый
`anchorTx`, каждый `payoutTx`.

Серверное развёртывание (systemd-юниты на каждый узел/сайдкар/координатор, nginx с CORS на одном
публичном порту) описано в `backend/deploy/README.md`; базовый URL и аккаунт пула общего testnet-
инстанса передаются вне репозитория (никогда не коммитятся). Когда поднят TLS-сайт
(`backend/deploy/README.md`, «HTTPS on a domain»), публичный базовый URL — `https://confidant.im/api`;
браузерный UI ходит в `/api/` своего же origin. `backend/quorum/smoke.mjs` — полный
клиент контракта: shield, transfer, unshield, reveal против любого работающего координатора:

```bash
cd backend/quorum && POOL=<pool> COORDINATOR_URL=http://<host>:8787 CLI=../../target/release/examples/cli npm run smoke
```

## 6. Как меняется контракт

- **Добавление** поля в ответ обратно совместимо: достаточно попросить (issue или комментарий к PR),
  делается в тот же день.
- **Переименование/удаление** полей и **новые эндпоинты** — через PR, затрагивающий `backend/`; если
  меняется путь доверия (что проверяет узел, что подписывает сайдкар), сначала нужно решение аудитора
  по срезу; чистое изменение формы API — однострочное FYI аудитору.
- Контракт выше заморожен до конца хакатона, если оба лида не договорятся об ином в PR.
- 2026-10-11: добавлена протокольная комиссия (`Accepted.fee`, нетто `payout.amount`,
  `GET /config.fees`, `GET /fees`, `POST /fees/sweep`); UI строит ноту shield за вычетом комиссии (§2).
- 2026-10-21: `GET /fees.outstandingBacking` (публичная сумма пула); UI показывает её в строке
  статуса и под приватным балансом (§2).

## 6a. Прототип (2026-10-10)

**Доказательство в браузере — бюджет и то, что менять нельзя** (замер 2026-10-23 на живом сайте, Chrome,
ноутбук 20 ядер, изолированный контекст, `performance.measureUserAgentSpecificMemory`): воркер кошелька
держит ≈ 70 МБ после построения ключа доказательства и ≈ 135 МБ после первого доказательства — линейная
память WebAssembly не сжимается, это рабочий набор сессии; многопоточная сборка объявляет максимум
2 ГиБ shared-памяти (`frontend/wasm/build-threads.sh`), с большим запасом. Время: ключи 6,0 с и
доказательство на 2 действия 3,1 с на 16 потоках; ≈ 12 с и ≈ 16 с в один поток. Три факта делают это
дёшево, и UI их не меняет: (1) схема — Zcash Orchard Action **без изменений**, её размер (`k`) задан
Orchard, настраивать нечего; (2) **внутри доказательства нет арифметики неродных кривых** — авторизация
траты — RedPallas на Pallas, родная для схемы; все подписи XRPL (secp256k1 / ed25519) делает `xrpl.js`
вне доказательства, а депозит связывается memo (хешем бандла), который каждая нода сверяет с леджером,
поэтому lookup-библиотеки кривых (в стиле PSE / Axiom) не нужны и добавлять их нельзя; (3) доказательство
всегда строится в `wallet-worker.js`, никогда в основном потоке. Потокам нужна cross-origin-изолированная
страница: заголовки COOP/COEP *и* secure context (HTTPS или `http://localhost`); по голому `http://<ip>/`
браузер игнорирует заголовки, и кошелёк молча работает в один поток (карточка кошелька показывает «N threads»).
Аллокатор — стандартный; `wee_alloc` не поддерживается и не стоит своих известных утечек.

`frontend/index.html` — рабочая первая версия, от которой стартует FE-команда: одна статическая
страница без сборки. Кошелёк **в браузере**: `frontend/wasm` (confidant-core за wasm-bindgen, сборка
`wasm-pack build frontend/wasm --target web --out-dir ../pkg`) работает в `frontend/wallet-worker.js`;
страница хранит JSON `WalletSecret` в `localStorage`, синхронизируется из `GET /api/log`, воркер
собирает `{record, bundleHash}` для `POST /api/submit/*`. `xrpl.js` в браузере делает faucet и
депозит. Запасной вариант без WebAssembly: демо-сервис кошелька (`backend/wallet`: `POST /wallets`,
`GET /wallets/{id}`, `POST /wallets/{id}/{shield|transfer|unshield}`), который хранит ключи трат
демо-кошельков на демо-хосте — так и говорить. **Только для testnet-демо, и это не должно перейти на реальную ценность:**
кастодиальный сервис кошелька никогда не путь для пула на mainnet или с реальным XRP; браузерный
(WASM) кошелёк — production-путь, сервис с ним не «взрослеет». `?demo=1` показывает страницу на имитированных данных. Сайт nginx:
`backend/deploy/nginx/confidant-ui.conf` (порт 80). Смоук пути UI без браузера: `npm run smoke-ui`
в `backend/quorum`.
