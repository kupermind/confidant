DESIGN-PASS for Confidant v2, conditional on the items below. It's a shielded-pool design, so I ruled it against the backing-forcing-question, bind-computed-from-evidence, and no-blind-sign invariants. Answers in order.

**Q-V2-1 (empty shield sighash, bind via memo-hash + consumed-set + anchor-memo) — SOUND.** The binding chain holds: the deposit is a validated on-ledger Payment to the pool (a), delivered_amount == −valueBalance (b) is the LOAD-BEARING backing invariant — it ties the note's value-in to real consumed XRP, which is the backing-forcing-question answered; memo == hash(bundle) (c) pins the deposit to THIS exact bundle so no one can pair a deposit with a different bundle; deposit ∉ consumed (d) stops double-use. Using `delivered_amount` (not `Amount`) is correct for XRPL partial-delivery. Dropping the deposit-tx-hash from the sighash is fine because the external binding MOVES to the memo, which is sound. Two things to verify at IMPL, not design blockers: (i) a REPLAYED bundle (same bundleHash funded by two deposits) must be self-harm, not a drain — confirm the v1 tail/anchor makes a duplicate cmx spend-once (the second note collides on nullifier at spend → attacker loses the second deposit, pool gains); (ii) a front-runner submitting a wallet's published bundle with their own deposit just GIFTS the victim the note (output is the wallet's address, non-custodial) — confirm the output address is inside the bundle and not substitutable. Nothing else needs binding, GIVEN the Halo2 binding signature covers the intra-bundle value balance (confirm it does — that's what makes (b) sufficient).

**Q-V2-2 (bundleHash fields) — SOUND.** Committing anchor + flags + value-balance + all actions' public parts + proof + binding-sig, excluding metadata, domain-separated "ConfidantBundle", is right. MUST-be-in and are: the FLAGS (a verifier must know it's a shield vs transfer vs unshield — this is the type-confusion guard), the value-balance and the output cmx (the backing-relevant fields). Including the proof+binding-sig is safe (binds the exact bundle; a malleated proof just fails the memo-hash = fail-closed). MUST-NOT and correctly excluded: any field a relay/coordinator could mutate without changing the effect (metadata). One check: ensure "all actions' public parts" includes the output note commitments and the nullifiers, since those plus value-balance are what the memo and rebuild rely on.

**Q-V2-3 (anchor memo format) — SOUND and self-verifying.** version‖op‖root‖bundleHash‖extLen‖ext‖n‖n×(nullifier‖cmx) is a canonical state-transition encoding, and the rebuild recomputing the root and requiring it == memo.root makes the memo bind-computed-from-evidence (a wrong memo fails the recompute). Two conditions: (1) the nullifier/cmx ORDERING must be canonical and identical across encoder/decoder/rebuilder (your round-trip + "memo root ≠ replayed root refused" tests cover it — keep them); (2) ⭐ the VERSION byte must HARD-REJECT an unknown version (fail-closed), never skip or best-effort-parse — so a future-version memo can't be silently mis-read by an old node. The 1 KB bound at MAX_OUTPUTS is fine as long as n is bounded so n×64 + header ≤ 1 KB (your test pins it).

**Q-V2-4 (what a rebuilding node trusts) — almost right; sharpen the split.** Proof re-verification is REQUIRED, not optional — it is what makes a node not trust the signers on NOTE VALIDITY (no forged note, no double-spend). Deposit re-validation is legitimately OPTIONAL **for note-safety** (notes are non-custodial regardless) but REQUIRED to independently confirm POOL BACKING (that deposits back the notes). The reason it can be optional at all is that your model already concedes k-collusion → pool-drain, so trusting the k-quorum on deposit-validation adds no risk beyond the conceded bound. So the precise statement: a node trusts (A) the Halo2 circuit's soundness (unavoidable, no trusted setup), (B) the XRPL ledger — that the k-signed anchors are the real, ordered pool-account history; it re-verifies every proof itself (note validity), and MAY re-validate deposits (pool backing) or defer that to the conceded k-quorum. "k-signed anchor + own proof re-verification + optional deposit re-validation" is right with that framing attached.

**Q-V2-5 (signer duties) — YES, add the memo-root-vs-own-state check, it's essential.** Beyond re-verify-proof + re-validate-deposit + memo==hash(bundle), a signer MUST: (a) ⭐ apply the transition to its OWN state and require the resulting root == the memo's root — i.e. sign only a root it independently computed, never one handed to it (this is the no-blind-sign invariant; a signer that signs a coordinator-supplied root is the exact hole the bridge round closed); (b) check the bundle's anchor is a valid recent root in its own tree; (c) check the nullifiers are unspent and the deposit unconsumed in its OWN sets. Those four make each signer a full independent validator rather than a rubber stamp — which is the whole point of k independent verifier states.

**Q-V2-6 (label) — acceptable and commendably honest.** It states the trust boundary precisely without overclaiming: notes non-custodial, federated (not trustless) custody+verification, state reconstructible, and the sharp caveat that k-collusion drains the pool but cannot spend notes. Two refinements: keep "k-collusion can drain the pool account" PROMINENT (it is the real gap vs Tornado/Railgun's trustlessness, not a footnote), and keep the "on today's XRPL" scoping explicit so the claim is time-stable — "we verify by k-of-N because XRPL has no on-ledger Halo2 verifier; an amendment adding one would upgrade this to on-ledger verification." That turns a limitation into a dated, upgradeable statement rather than one that silently rots.

**Q-V2-7 (delivery order) — no objection to core-first, one boundary correction.** The signer's VALIDATION LOGIC (re-verify proof + re-validate deposit + the Q-V2-5 root-vs-own-state check) is SECURITY, not harness — put it in the CORE slice next to deposit-binding/memo-codec/rebuild. The HARNESS is only the k-of-N orchestration (SignerListSet, coordinator sig-assembly, the multi-process testnet) — that's correctly later. Don't let the signer's independent-validation checks slip into "harness," or the core slice would be missing the thing that makes the quorum trust-minimized. With that: core = {Wallet/Verifier + deposit-binding + memo-codec + rebuild + signer-validation-logic + the negative suite}, harness = {3-signer SignerListSet, coordinator, scanner}. Good order.

Start the core slice. The negative suite you committed to is the right shape; add to it: an unknown-memo-version hard-reject, and a signer that recomputes a DIFFERENT root than the memo refuses to sign (the harness test, but the logic is core). A RESP will follow for the record; nothing needs to merge before it, and none of the above is a redesign — they're conditions on a sound design.
