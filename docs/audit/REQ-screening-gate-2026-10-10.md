REQ (design + impl in one, small slice): boundary screening gate in backend/node — branch screening-gate, PR #20. Owner's decision 2026-10-10: the cheap form of "proof of innocence" now (this), the per-note ZK form stays ROADMAP §4.5.4 (Railgun PPOI assessed: its node/list infra is reusable, its circom/Groth16 proof over Railgun's BN254 note format is not portable to Orchard). Trust-path change (new refusals, fail-closed), so a ruling before merge.

== Design ==
Every verifier node may carry its own policy: --screening-list FILE (XRPL addresses, one per line with # comments, or a JSON array; e.g. OFAC SDN "Digital Currency Address - XRP" via backend/quorum/screening/fetch-ofac.mjs — today exactly 1 entry on the SDN list) and --screening-standby-ledgers N. The node refuses with NodeError::Screened → HTTP 403, BEFORE the core verifier sees the bundle: (a) a shield whose deposit's sender account is listed; (b) a shield whose deposit validated fewer than N ledgers before the latest validated ledger (Railgun's unshield-only standby: 1 h ≈ 900 XRPL ledgers; the demo runs 2); (c) an unshield whose destination is listed. Enforced at POST /submit/shield, /submit/unshield AND at /endorse for both ops — a coordinator cannot route around a signer's list; a quorum with the gate on since genesis admits no note descending from a listed address, which anyone can re-check from the public log + ledger (screening/audit.mjs: shield → deposit tx → Account; unshield → destination). Inputs come from the ledger only: deposit_source(tx) reads Account and ledger_index from the same `tx` answer the node already fetched for deposit_facts; the validated index from `ledger` (ledger_index: validated) through a new Ledger::validated_ledger_index, read only when standby > 0; nothing from the client or the coordinator. Fail-closed: an unavailable validated index refuses (Rpc error), a missing Account/ledger_index refuses (Deposit error). Gate off = no list and standby 0 → no extra ledger call, behaviour unchanged. Replay (rebuild_checked) does NOT re-screen history by design (lists change; it is an acceptance-time policy). Honest label in SPEC/README/CLAUDE: gatekeeping on public data at the public boundary, not per-note PoI; lists can be wrong or late; a refused deposit stays in the pool account until a quorum refund (manual; ROADMAP §4.3a = sidecar shape rule for refunds, a future slice).

== Code ==
backend/node/src/screening.rs (Screening {blocked: HashSet, standby_ledgers}, from_file, is_active, check_deposit(account, deposit_ledger, validated), check_destination; ScreenError Blocked / Standby), xrpl.rs (deposit_source, Ledger::validated_ledger_index), rpc.rs (`ledger` call, v1/v2 shapes), node.rs (Node::with_screening; screened_deposit used by submit_shield and endorse(Shield); screened_destination used by submit_unshield and endorse(Unshield); NodeError::Screened), http.rs (403), main.rs (flags; startup log "screening: N listed addresses, standby M ledgers" or "OFF"). JS: launchQuorum / start-all / render-env / systemd unit pass the flags; backend/quorum/screening/fetch-ofac.mjs and audit.mjs; e2e/testnet/run-services.mjs negatives. Docs: SPEC §6 (EN/RU), README labels, API-BOUNDARY 403 (EN/RU), NODE-OPERATOR, backend/README, deploy README, CLAUDE.md, ROADMAP (§1 row, §4.3a refund, §4.5.4 expensive variant, §7 risk), E2E §2b.

## Supplement — must-fix applied (2026-10-10)

Sent after the auditor's CONDITIONAL PASS (destination canonicalization), verbatim.

REQ supplement — must-fix applied (PR #20, branch screening-gate, latest commit): destination screening now compares addresses in one canonical form.

== Fix ==
backend/node/src/address.rs: base58check with the XRPL alphabet and the double-SHA-256 checksum verified on decode; a classic address (0x00 ‖ AccountID) and an X-address (prefix 0x0544 mainnet / 0x0493 testnet ‖ AccountID ‖ tag flag ≤ 1 ‖ 8-byte tag) both decode to the 20-byte AccountID; canonical() re-encodes the classic address with the tag dropped; anything else (bad checksum, wrong length, foreign alphabet, foreign prefix, unknown tag flag) → None. screening.rs: canon() is applied at list load (Screening::new / from_file) AND at every lookup (is_listed, used by check_deposit and check_destination), so list entries, the ledger-read sender and the client-supplied destination are compared in the same form; an undecodable list entry matches only itself. New dependency: sha2 0.10 (RustCrypto); no new I/O.

== Your precondition question: live or latent? ==
Latent, by accident, not by the gate's doing: xrpl.js autofill converts an X-address Destination to classic + DestinationTag, and the sidecar's shape rule compares the converted tx.Destination with its own node's raw payout.destination (the X string) → "destination differs" → refused. The gate did not own that reject; now it does (and the sidecar's string compare stays as a second, independent layer).

== Minor confirm: main.rs propagates from_file errors ==
Yes — `Screening::from_file(...).unwrap_or_else(|e| die(...))`, parsed before the ledger is even opened: `confidant-node … --screening-list /nonexistent/list.txt` prints `error: --screening-list /nonexistent/list.txt: No such file or directory (os error 2)` and exits 1; a bad JSON array exits the same way. Never a silently empty list.
